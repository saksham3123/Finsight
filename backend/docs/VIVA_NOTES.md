# FinSight Backend — Viva Notes

## Stage 1 — Project setup

**Q1. Why separate `app.js` and `server.js`?**
`app.js` only builds the Express app; `server.js` loads config and calls `listen()`. Tests can then import the app and send requests to it (e.g. with Supertest) without starting a real server or using a port, and startup logic stays apart from request handling.

**Q2. What do `helmet` and `cors` protect against, and why not allow all origins?**
Helmet sets security headers: HSTS forces HTTPS, `X-Content-Type-Options: nosniff` stops MIME sniffing, and frame and content-security policies reduce clickjacking and XSS. CORS tells browsers which other origins may call the API. Allowing only the React app's origin means a malicious site open in the same browser can't read API responses. `*` would allow any site.

**Q3. Why keep secrets in `.env`, and why have two health endpoints?**
Secrets in code end up in git history permanently. `.env` is git-ignored, and `.env.example` documents the variables without values. The server exits at startup if a required variable is missing. `/api/health` is a liveness check (the process is up). `/api/health/db` is a readiness check (it can reach PostgreSQL). Keeping them separate shows whether a failure is in the app or in the database.

## Stage 2 — Database

**Q1. Why UUIDs instead of auto-increment integers? Where did you not use them?**
UUIDs can't be guessed (no `/users/1`, `/users/2` enumeration), can be generated by any service without collisions, and don't reveal row counts. The cost is 16 bytes instead of 4 and slightly slower index inserts. `price_history` uses the natural key `(asset_id, date)` because each asset has exactly one candle per day. `user_preferences` uses `user_id` because each user has exactly one row.

**Q2. Why is money stored as `NUMERIC` and not `FLOAT`? What does `pg` return for it?**
Binary floating-point can't store values like 0.1 exactly, so totals drift (0.1 + 0.2 ≠ 0.3). `NUMERIC` is exact decimal arithmetic. Eight decimal places cover crypto down to one satoshi. The `pg` driver returns `NUMERIC` as a string so precision isn't lost by converting it to a JavaScript number.

**Q3. Most foreign keys cascade on delete. Why do `audit_log` and `transactions.sip_plan_id` use `SET NULL`?**
Cascade keeps the database consistent when a user is deleted: no orphaned watchlists or tokens. But an audit log exists to record what happened, so deleting the user must not delete it. The row stays and only the link is cleared. Similarly, trades a SIP already executed are real history and must remain if the SIP plan is removed.

**Bonus — How is the schema idempotent, and why does migrate use a transaction?**
Every table and index uses `IF NOT EXISTS`, so re-running is harmless. PostgreSQL supports transactional DDL, so wrapping the whole file in `BEGIN/COMMIT` means a mid-file error rolls everything back and never leaves a half-built schema.

## Stage 3 — Authentication and users

**Q1. Why use both an access token and a refresh token? Why not one long-lived JWT?**
A JWT is checked by signature alone, with no database lookup, so it can't be cancelled before it expires. Keeping the access token short (15 minutes) limits the damage if one is stolen. The refresh token is long-lived (30 days), but it's only sent to `/auth/refresh` and it's stored in the database (as a SHA-256 hash), so it can be revoked on logout or password change. Together they give both speed and the ability to revoke.

**Q2. What is refresh-token rotation and how do you detect a stolen token?**
Every refresh consumes the old token and issues a new one. Only one party should ever hold the current token. If a token that was already used shows up again, either the attacker or the real user is replaying an old copy, and the server can't tell which. So it revokes every session of that user and logs `auth.refresh_token_reuse`. The row is locked with `FOR UPDATE`, so two simultaneous refreshes can't both win.

**Q3. How do you stop attackers guessing passwords or finding out which emails are registered?**
- Passwords are hashed with bcrypt at cost 12, which is deliberately slow and salted per user, so cracking leaked hashes is expensive.
- Login and register are rate limited to 20 attempts per IP per 15 minutes (HTTP 429).
- An unknown email and a wrong password get the same message.
- When the email doesn't exist, the password is still checked against a dummy bcrypt hash, so both cases take the same time. Without that, a fast "no such user" reply would reveal which emails are registered.

## Stage 4 — Assets and market data

**Q1. How do you return the latest price for every asset in one query?**
With `LEFT JOIN LATERAL (SELECT close FROM price_history WHERE asset_id = a.id ORDER BY date DESC LIMIT 1)`. LATERAL lets the subquery refer to the current asset row. Because `(asset_id, date)` is the primary key, each lookup is a quick backward index scan rather than a scan of all prices. A second LATERAL with `OFFSET 1` gets the previous close for the daily % change.

**Q2. Why did you change how pg returns DATE columns?**
By default pg turns a `DATE` into a JavaScript `Date` at local midnight. In India (UTC+05:30), `2026-11-12 00:00 IST` serialises to `2026-11-11T18:30:00Z`, so the API would show the previous day. A type parser now returns the plain `YYYY-MM-DD` string. A test checks the format.

**Q3. How is price data ingested, and how do you avoid duplicates?**
`PUT /assets/:id/prices` (admin or ML service key) and the CSV import script share the same validation and a single `INSERT ... SELECT FROM unnest(arrays) ON CONFLICT (asset_id, date) DO UPDATE`. One statement handles thousands of rows, and the primary key guarantees one candle per day, so re-importing the same file just overwrites it. Bad rows (e.g. high below low) are rejected by validation and by `CHECK` constraints.

## Stage 5 — Portfolio and SIPs

**Q1. How is the average buy price calculated, and why in SQL instead of JavaScript?**
Weighted average: `(old_qty × old_avg + new_qty × price) / (old_qty + new_qty)`, run inside `INSERT ... ON CONFLICT DO UPDATE` on `NUMERIC` columns. Doing it in SQL keeps it exact (JavaScript floats can't represent most decimals) and atomic with the transaction insert. For example, 10 shares at 3000 plus 5 at 3600 gives exactly 3200.00000000, which a test checks.

**Q2. What stops a user selling the same shares twice with two simultaneous requests?**
The sell is a single conditional statement: `UPDATE holdings SET quantity = quantity - $q WHERE user_id = $u AND asset_id = $a AND quantity >= $q`. PostgreSQL locks the row while updating, so the second request sees the reduced quantity. If not enough remains, it updates nothing, and the API returns 400 and rolls back. The holding update and the ledger insert run in one database transaction, so they can never disagree.

**Q3. How do SIPs run, and what happens if the server was down for two months?**
A scheduler (in-process timer, `npm run sips:run`, or the admin endpoint) finds active plans with `next_run_date <= today`. Each one runs in its own transaction with `FOR UPDATE SKIP LOCKED`, so parallel runs never execute a plan twice. It buys `amount / latest close` units and moves `next_run_date` forward. Missed periods aren't back-filled: the plan runs once and jumps to the next future date, because buying two months' worth at today's price would misrepresent a SIP. Plans past their end date become `completed`.

## Stage 6 — Advisories and news (ML integration)

**Q1. How does the ML service write data without a user account?**
It sends a shared secret in the `X-Service-Key` header. The server compares it with `crypto.timingSafeEqual`, which takes the same time whatever the input, so the key can't be guessed character by character from response times. Admins can call the same ingestion endpoints with their JWT. Anything else gets 401 or 403.

**Q2. How do you guarantee one advisory per asset per day, and avoid duplicate news?**
A `UNIQUE (asset_id, advisory_date)` constraint plus `INSERT ... ON CONFLICT DO UPDATE`, so re-running the model replaces that day's advisory. For news, `UNIQUE NULLS NOT DISTINCT (asset_id, url)` is needed. Normally two NULLs count as different, so the same market-wide article (no asset) could be stored twice. `NULLS NOT DISTINCT` (PostgreSQL 15+) treats them as equal.

**Q3. Explain your baseline advisory engine. Is it a prediction model?**
No. It's a rule-based technical-indicator baseline:
- It compares the 20-day and 50-day moving averages for trend.
- It uses annualised volatility of daily log returns as the risk score.
- It optionally adjusts using 7-day news sentiment.
- A large positive gap with the price above SMA20 gives `buy`, the reverse gives `sell`, a small gap gives `hold`, very high volatility gives `high_risk`, and anything else gives `watch`.

It's explainable (every advisory includes its numbers), gives the app real advisories before the ML model exists, and acts as the baseline the ML model must beat. It never overwrites an ML advisory for the same day.

## Stage 7 — Chat assistant and audit log

**Q1. How does the chat assistant work, and why not use an LLM?**
It's rule-based. Keyword patterns detect the intent (portfolio, watchlist, SIPs, a mentioned asset, buy advice, help), and each intent runs SQL queries over the user's real data and the latest advisories. So it can't make up prices or holdings, it costs nothing, needs no external API, and every answer can be checked. The route only calls `generateReply()`, so an ML or LLM implementation can replace it later without changing the API.

**Q2. How do you keep one user's chat history away from another user?**
Every query filters by `user_id` from the verified JWT, never from the request body. Sending another user's `conversationId` returns 404, the same as one that doesn't exist, so the API doesn't even reveal that it exists. Tests cover both reading and posting into someone else's conversation.

**Q3. What do you audit, and how do you make sure audit rows are accurate?**
Security events (logins, failed logins, logout, token reuse, password change, account deletion, role changes) and data changes (trades, SIP changes and executions, asset edits). For data changes, the audit row is written with the same transaction client as the change. If the change rolls back, so does the audit row, so the log never records something that didn't happen. Audit rows keep `user_id ON DELETE SET NULL`, so they survive account deletion.

## Stage 8 — Testing and quality

**Q1. How did you test the backend?**
- 60 automated tests use Node's built-in `node:test` runner and `fetch`, with no extra libraries. Each test file rebuilds a separate `finsight_test` database, starts the real app on a random port and sends real HTTP requests, so middleware, SQL and database constraints are all exercised.
- A Postman collection (35 requests, 44 assertions) runs the full user journey headless with the Postman CLI.

**Q2. The test setup drops the whole schema. How do you make sure it never wipes the real database?**
It refuses to run unless the database name ends in `_test`, checked twice: once on `TEST_DATABASE_URL`, and again on the live connection with `SELECT current_database()`. The second check exists because code review found that a test importing an app module before the test helper would have opened the pool against the dev database. The import order was fixed as well.

**Q3. What are the main limitations of the current backend?**
- The rate limiter is in-memory, so it doesn't work across several server instances.
- The refresh token is sent in the response body instead of an httpOnly cookie, which makes it XSS-exposed.
- SIPs buy fractional units.
- Portfolio totals aren't converted between INR and USD.
- Advisories come from a simple baseline until the ML model is connected.
- Sample prices are synthetic.
- The schema upgrades re-run each migrate, because PL/pgSQL is blocked on the dev machine.

## Stage 9 — Range forecasts

**Q1. How did you add range forecasts to the database without breaking existing data?**
Five nullable columns on `advisories`, added with `ALTER TABLE … ADD COLUMN IF NOT EXISTS` so the migration is safe to re-run and old rows stay valid. A CHECK constraint enforces all-or-nothing range fields, positive prices, low ≤ high, a level strictly between 0 and 1 and a horizon of 1–60 days.

**Q2. Why validate the range in both the API and the database?**
The API gives clients a clear error message ("priceHigh must be >= priceLow"). The database constraint is the last line of defence: no code path, including a manual SQL insert or a future bug, can store an impossible range.

**Q3. Why does the chat assistant mention the range before the buy/sell signal?**
The ML evaluation showed the range forecast has statistically reliable skill and the direction signal doesn't. Putting the more trustworthy information first is part of presenting model output honestly.
